### <a name="_qmphm5d6rvi3"></a>**Решение**

- [context diagram](context_diagram.puml)
- [container diagram](container_diagram.puml)

В предлагаемом решении введен новый компонент "Сервис управления депозитами",
который становится центральной точкой для работы с депозитными продуктами. Это позволяет:

- Централизовать управление ставками
    - Замена Excel-файлов структурированным хранилищем
    - Единый источник информации о ставках для всех каналов
    - Снизить нагрузку на АБС

- Организация промежуточного слоя между клиентскими приложениями и АБС
    - Кэширование часто запрашиваемых данных
    - Обеспечить масштабируемость

- Сервис управления депозитами построен на микросервисной архитектуре
    - Возможность горизонтального масштабирования компонентов
    - Использовать существующие технологии

- Сохранение основных технологических стеков (.NET, Oracle, MS SQL)
    - Для новых компонентов выбраны технологии с имеющейся экспертизой (Java)
    - Реализация API для интеграции компонентов осуществляется через REST API с шифрованием данных по HTTPS, что
      обеспечивает безопасную передачу данных.

### <a name="_bjrr7veeh80c"></a>**Альтернативы**

- Доработка существующего интернет-банка без внедрения нового сервиса
    - Преимущества: меньше компонентов, более простая архитектура
    - Недостатки: сложнее обеспечить масштабируемость, высокая нагрузка на АБС, сложнее модифицировать монолит

- Полная замена интернет-банка на микросервисную архитектуру
    - Преимущества: гибкая масштабируемость, изолированность компонентов
    - Недостатки: высокая стоимость миграции, требуется переобучение персонала, избыточно для текущих потребностей

- Использование внешнего SaaS-решения для управления депозитами
    - Преимущества: быстрое внедрение, готовая функциональность
    - Недостатки: зависимость от внешнего поставщика, проблемы с интеграцией, риски для безопасности данных

**Недостатки, ограничения, риски**

#### Недостатки:

- Введение дополнительного компонента усложняет общую архитектуру
- Необходимость реализации дополнительных интеграционных потоков
- Потребность в синхронизации данных между несколькими системами
- Дополнительные затраты на разработку и сопровождение нового сервиса

#### Ограничения:

- АБС остается узким местом в архитектуре (вертикальное масштабирование)
- Интеграция с существующими системами потребует доработки их API
- Существующая инфраструктура интернет-банка требует доработки для обеспечения высокой доступности

#### Риски:

- Риск несогласованности данных между системами при сбоях в синхронизации
- Риск превышения ожидаемой нагрузки на новый сервис
- Вероятность возникновения задержек при интеграции компонентов
- Сложности миграции данных о ставках из Excel-файлов в новую систему
- Потенциальные проблемы с обеспечением требуемого уровня доступности (99,9%)
- Риск недооценки затрат на разработку и интеграцию
